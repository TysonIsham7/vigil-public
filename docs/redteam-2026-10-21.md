## RT-01 — High Security does not hold the document

**Severity:** High

**Where:** `apps/extension/src/background.ts` (`noteNavigation`, `onNavigate`), `apps/extension/src/dnr.ts`, `packages/core/src/navigate.ts` (`canonicalHost`)

`onBeforeNavigate` is not cancelable. High Security decides to hold only after storage reads, then updates the tab to the hold page. Session rules redirect to the hold page only for hosts already cached as hold or block, and only for the main frame. A first visit to an unknown origin has no synchronous block.

The 2 second budget does not cover this gap. The hold scan starts its clock when the hold page has already loaded and asked for a scan. Service-worker startup sits in front of that. A native host that answers inside the budget, including with a clean verdict, does not undo script that already ran. A host that never answers does keep the hold page up, but only after the redirect has won the race.

Host canonicalization returns no host for anything that is not an http(s) navigation, and for any navigation with userinfo. The navigation handler treats that as "do nothing", so the navigation is not failed closed. The browser still blocks most top-level data navigations. It does not block top-level blob documents or blank documents. A blank document opened and then written by script never has a host, so the gate never runs. A userinfo navigation is ignored when the event still carries the userinfo.

Subframes are ignored. A top-level page that High Security has allowed, or a blank window, can show a full-window frame of any other origin. The framed document loads and paints. That is enough for a credential form. The parent does not receive the frame's DOM.

Server redirects are a second race. An allowlisted hop does not intercept. The committed next hop starts another async tab update. The committed document can run until that update lands. The return check does stop the hold page from navigating to a script scheme or a different host. It does not stop the document that already committed.

**Fix:** While High Security is on, install a session rule that redirects every main-frame http(s) navigation to the hold page, excluding the allowlist and the one-time hosts. Remove that rule only for a host the check has already allowed. Treat a top-level document that is not http(s) and not the extension hold page as a hold, including blank and blob documents. Block, rather than show a second hold UI, subframe requests whose host is not the top frame's already-allowed host. Start the deadline when navigation is about to start, and ignore a verdict that arrives after it.

## RT-02 — The loopback helper is an unauthenticated GET, and errors fail open

**Severity:** High

**Where:** `packages/netcheck/src/serve.ts`, `apps/extension/src/scan.ts` (`helperVerdict`), `apps/extension/src/background.ts` (`holdScan`)

The published fallback listens on loopback only. That stops a remote host from dialing it. It does not stop a browser on the same machine.

What the server does not do:

- It never reads the host header, the origin, or the fetch-site header.
- It sets no cross-origin allow header. A normal cross-origin read fails. A DNS-rebinding read does not need one.
- The route is a GET with the target in the query string. No token, no POST, no custom header.
- The only limit is 60 requests per minute for the whole process.

A page can issue those GETs without reading the body. Current Chrome often blocks a public site from touching loopback. Firefox does not implement that the same way, and that browser check is not a substitute for a host-header allowlist. After a name flips from the attacker's address to loopback, the browser treats the follow-up as same-origin, and this server answers the foreign host header anyway.

The extension trusts the JSON. An empty signal list for the matching host is a full-coverage allow, and it is cached for a day. Anything bound to that port can do this, including a process that wins the port before the helper. The hold page renders the returned title and summary as text, so the same process also chooses the words next to the proceed button.

Fail-open is separate from forgery. The helper client holds only on a gateway timeout, a host mismatch, or an abort. Every other non-OK status, and any thrown redirect, is treated as a finished local check. For a host with no local lookalike signal that is an allow. The background page then marks the helper down, and the next navigation is allowed to reuse that local allow. The extension notes say a refused connection should fall back to the local check. A web page can force that path by spending the request budget, including against a host whose only gating signals would have come from the certificate check.

The helper fetch does not bypass the HTTP cache. A peer that omits the server's no-store header can leave an allow in the cache.

**Fix:** On startup, print a one-time token and require it on a header so the browser must preflight. Reject every request whose host header is not loopback with the bound port. Ignore origins other than the extension, and reject browser fetch-site values that are not the extension's own. In the extension, treat every helper failure except a matching, well-formed verdict as a hold when the mode is high. Do not cache that failure as allow, and do not mark the helper down because it returned a rate limit. Bypass the HTTP cache. Prefer the native host, which the browser starts itself, and refuse to fall back to a port any process can bind.

## RT-03 — Private addresses are still dialed

**Severity:** High

**Where:** `packages/netcheck/src/cert.ts` (`connectCertificateChain`), `packages/netcheck/src/verdict.ts` (`hostVerdict`), `packages/netcheck/src/fetch.ts` (`safeFetch`), `packages/core/src/ssrf.ts`, `packages/netcheck/src/rdap.ts`

The verdict starts the TLS dial and the HTTP fetch together. Only the HTTP path checks the resolved address. The TLS path has no lookup hook and no private-address check. Accepting an unauthorized certificate is appropriate for inspection, and the socket is closed after the handshake, so this path does not send an HTTP request. It does complete a TLS handshake to whatever address the name resolves to, including loopback, private, and link-local ranges. DNS names that look public and resolve to those ranges pass the URL filter. The HTTP path would refuse them. The certificate dial happens anyway.

A page cannot open the native-messaging pipe (RT-10), but the extension sends that pipe the host of the tab, and the loopback helper accepts any host query (RT-02). Either one will dial a name the caller chooses. Browser private-network checks do not apply to the runtime's TLS client. The usual metadata HTTP service is not requested here. The dial is the TLS port. Internal HTTPS services still see a handshake from the helper process.

The HTTP fetch has a second hole. It resolves the name, then fetches the hostname, which resolves again. A name that is public for the first lookup and private for the second is a normal HTTPS GET to the private address. Redirects are re-checked, then fetched the same way.

The URL filter also allows literals that embed a private IPv4 address. Ordinary loopback spellings, including mapped IPv6 forms the parser rewrites, are rejected. The NAT64 well-known prefix, 6to4 when it embeds a private address, deprecated site-local space, multicast, and the limited broadcast are allowed. For an allowed literal the resolver check returns immediately because the address is not on the denylist. On a network that implements NAT64, the well-known prefix reaches the embedded address.

Domain-age lookup fetches the public RDAP bootstrap and then the registry URL it names, with redirects followed. That registry URL is not passed through the URL filter. A redirect from that server toward a link-local metadata address is a blind GET. The body is reduced to an age in days, so this is not a metadata read-back. The domain is also interpolated into the path without encoding. Labels that survive the URL filter are unlikely to change the path. Encode them anyway.

**Fix:** Resolve once, refuse the whole verdict if any address is blocked, and pass that address to both clients. Pin the TLS lookup and the HTTP client to that address, and pin again on every redirect. Extend the denylist to the NAT64 well-known prefix, 6to4 when the embedded IPv4 is blocked, deprecated site-local space, multicast, and the limited broadcast. Run RDAP URLs through the same filter, follow redirects manually, and encode the domain.

## RT-04 — The hold page is easy to imitate

**Severity:** Medium

**Where:** `apps/extension/hold.html`, `apps/extension/src/hold.ts`

The hold UI is ordinary HTML in the tab. It does not show the hostname or the URL that the one-time proceed action will open. A site can paint the same heading, the same two buttons, and the same colors. Combined with RT-01, that paint can take the click before the tab is replaced. The real buttons call into the extension. The fake ones belong to the page.

The extension-page address bar is the only signal that cannot be copied, and the hold page does not tell the user to look at it. Signal titles returned by the helper are attacker-controlled whenever RT-02 applies. They are inserted as text, so they are not markup injection. They can still be the sentence next to the real button. Bidi characters in that sentence can reorder how the line looks.

**Fix:** Move the one-time proceed action and the always-allow action into the toolbar popup, which a page cannot draw. On the hold page, show the destination as text, with no override button. Reject signal titles and summaries that contain bidi overrides or characters outside a short allowlist, and cap their length.

## RT-05 — Safari certificate check trusts the JS hostname and a private parser

**Severity:** Medium

**Where:** `apps/safari/Shared (Extension)/SafariWebExtensionHandler.swift`, `apps/safari/Shared (Extension)/NativeCertCheck.swift`

A web page cannot call the native-message API. The extension sends the tab host as an https URL message. That message is still attacker-controlled input: the host is whoever the tab navigated to, including an open redirect's target. The Swift boundary is the right place to be strict.

What already holds:

- The dictionary must have one URL field, and the string must be https, short, with no userinfo, query, fragment, backslash, or non-empty path.
- Only the default HTTPS port is accepted. IPv6 literals and all-numeric hosts are rejected.
- Redirects are cancelled. The server-trust challenge is cancelled, so the connection does not proceed to an HTTP request.
- The challenge host must equal the requested host. Trust evaluation is not allowed to fetch extra certificates, so issuer URLs in the certificate are not retrieved.

What does not hold:

The DNS-name check accepts a name whose labels are not all numeric even when the name is built to resolve to loopback. The fetcher then starts a session for that host and never inspects the resolved address. The app opens the TLS port to loopback, private, or link-local destinations the tab name points at. The ephemeral session still follows the system proxy unless a proxy dictionary is set, so a malicious proxy configuration can steer the dial.

Distrust is decided by the hand-rolled certificate parser, not by system trust. System trust is only one input to the authorized flag. If the parser returns facts for every certificate but hashes the wrong key, a chain the system still trusts produces no distrusted-CA signal. A total parse failure does fail closed. The dangerous case is a parse that succeeds and is wrong. Case folding is locale-dependent. In a Turkish locale this tends to false-mismatch, which fails closed, rather than false-match. Folding should use a POSIX locale anyway.

**Fix:** Resolve the name and refuse non-global addresses before starting the request. Disable the system proxy for that session. Take the key identifier and validity from the system certificate APIs, and keep the DER parser only as a cross-check. Compare names with a POSIX locale.

## RT-06 — The snapshot scrub can miss a person, and the commit is not hermetic

**Severity:** Medium

**Where:** `publish/export.mjs`

The script copies tracked files, drops the publish tooling and the private handoff, strips one README section, and refuses the snapshot if a denylist matches. The denylist is specific to this repository's owner: a few name and machine-name expressions, one home-directory prefix with a placeholder exception, a private-key header, one allowed test file for device-model strings, and a placeholder team id. It does not look for other home-directory prefixes, email addresses, or common token prefixes. A new file that contains a different person will be published. Bytes are decoded as UTF-8, so UTF-16 text can hide the same strings. The check runs before the new repository is initialized, so that new git directory is not scanned. That part is fine.

The commit overrides the author and committer identity and turns signing off for that commit, but it also forwards the caller's environment. Git config supplied through the environment, and a global hooks path, still apply. A hook or an overridden template can write the real name, email, or signing identity into the snapshot commit. The destination is removed recursively once the path is merely outside the repo. Path resolution does not canonicalize symlinks.

**Fix:** Build the git environment from a fixed allowlist instead of forwarding the caller's environment. Disable hooks for the snapshot commit and use an empty home directory. Canonicalize the destination and refuse world-writable or non-empty paths unless a flag is set. Scan for email addresses, every home-directory prefix, and the token shapes the redaction helper already knows. Decode UTF-16 when a byte-order mark is present.

## RT-07 — CI runs code it did not hash

**Severity:** Medium

**Where:** `.github/workflows/ci.yml`, `pnpm-lock.yaml`, `apps/cli/package.json`

Runtime dependencies are small: workspace packages plus one pinned compression library, used to unzip scan input in memory after a relative-path check. There is no third-party postinstall in the production graph. Dev dependencies do run install scripts. The install is frozen to the lockfile. That is the right lock. It is not a digest pin of the CI tools.

The workflow then downloads two secret scanners by versioned release and runs them. The downloads are HTTPS and the versions are named. The assets are not checked against a published digest, and the tags are not immutable. A replaced release asset runs as the CI job and sees the checkout token. The checkout, package-manager, and runtime setup actions are floating tags with the same property.

The unzip helper has no output-size cap. A zip submitted to the scanner can expand until the process dies. That is availability of the CLI, not a publish-time supply-chain break.

**Fix:** Pin each Action to a full commit SHA. Store the expected digest of each scanner next to the workflow and verify it before extracting. Prefer turning install scripts off for the dev install, and allow the bundler's install explicitly if the build needs the native binary. Cap the uncompressed size when reading a zip.

## RT-08 — The vulnerability-watch skill is an indirect prompt-injection path

**Severity:** Medium

**Where:** `docs/agent-skill-vuln-watch.md`

The file itself is clean. It has no hidden bidi or zero-width characters, and it tells the agent that posts are data. The routine still requires the agent to read vendor blogs, status pages, vulnerability-database text, government alerts, and public posts, then decide what the user should do. Those pages are attacker-controlled. A post can claim to be the vendor, and the skill has no allowlist of accounts or hostnames to refute that. The instruction to use the official site depends on the model knowing which site is official.

The untrusted-content section is in the same prompt the fetched page is added to. A page that tells the agent to ignore that section is the usual indirect injection. The instruction to say what the user should do, usually upgrade or rotate a credential, is easy for an autonomous agent to read as permission to do it. The skill forbids copying commands into a terminal because a post said so. It does not give the agent a place to put the untrusted text where it cannot compete with those rules, and it does not forbid the agent from carrying out the remediation itself.

Publishing the snapshot publishes this skill for other people's agents.

**Fix:** Keep a fixed list of source hostnames and accounts in the skill. Fetch only those. Put fetched bodies in a quoted data block with a one-line reminder that nothing inside is an instruction. Require the report to be data: product, version, matched or not, source, and publication date. State that the agent must not change config, install packages, rotate secrets, send messages, or shell out, including when the user list says that product is theirs. Treat public posts as leads that are confirmed only after the vendor hostname is opened from the allowlist.

## RT-09 — Privileged messages do not check the sender

**Severity:** Low

**Where:** `apps/extension/src/background.ts` (`onMessage`)

Mode changes, helper changes, the one-time override, and the permanent allow are handled for every internal message sender. The manifests have no content script and no external messaging entry, and the hold page is not web-accessible, so a web origin cannot call this today. Any future content script, or any extra extension page, could turn High Security off or allowlist the tab's host. The hold scan and the overrides are also not limited to the hold page.

**Fix:** Allow mode and helper changes only from the popup. Allow the hold scan and both overrides only from the hold page in the tab that owns the saved navigation.

## RT-10 — Native messaging is not reachable from a page

**Severity:** Info

**Where:** `apps/cli/src/native-install.ts`, `packages/netcheck/src/native-host.ts`, `apps/extension/manifest.json`

The browser launches the host only for origins on the allowlist. The installer writes exactly one extension origin, and it rejects an id that is not the expected length and alphabet. The extension id is pinned by the public key in the manifest. There is no external-messaging entry. Another extension, and any web page, cannot open this pipe through the browser.

The host itself cannot see which extension connected. A process that can execute the wrapper and write to its standard input can request a verdict. That is the same local-user boundary as the rest of the machine. Replacing the allowlist requires write access to the user-level native-messaging directory.

Frames are length-prefixed. An empty frame or a frame over the small cap is rejected. Buffered input is capped just above that. JSON that is not a single host field is rejected before a verdict runs. A verdict timeout becomes a timeout error. Other exceptions become a generic rejection with no host and no error text. The existing native-host test covers the oversized frame and the extra-field rejection. Those checks matched the code.

The fetches that host performs are RT-03. The origin lock is not.

## What held up

- The helper-origin check accepts only loopback HTTP with no userinfo, path, query, or hash. Other spellings of that address normalize to the same origin. A localhost name, a public host, and HTTPS loopback are rejected.
- The return check rejects non-http schemes, extension pages, userinfo, and a different host before the hold page navigates back.
- Hold and popup text is assigned as text. Extension-page script policy allows only the extension itself, with no remote script and no update URL.
- The native-host reply does not echo internal exception text.
- Safari cancels redirects and the TLS challenge, and it does not let trust evaluation fetch issuer URLs.
- The exporter omits the private handoff and the publish tooling, and it overrides the commit identity when the environment does not fight it.
- Production npm dependencies are workspace packages plus one pinned compression library. The lockfile is frozen in CI.
